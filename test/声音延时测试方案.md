# 声音延时测试方案

## 1. 背景与目标

NUI 使用 sherpa-onnx 离线神经语音（int8 VITS 模型）播报天气、切换音色提示等。车机 CPU 性能弱（Android 9/32 位），**合成本身的推理耗时无法消除**，但通过"流式合成"（边合成边播放）、"双引擎缓存"（切换过的音色不释放）和"打断机制"（新播报优先）已把**感知延迟**降到最低。

本方案量化验证以下三个指标，确认优化在真实车机上的效果：

| 指标 | 含义 | 期望 |
|---|---|---|
| **T1** | 点击切换男女声 → 第一段声音（"正在切换…"或"主人好，我是xx"）出声 | < 1s（缓存命中）/ 首段 < 0.5s |
| **T2** | 第一段声音结束 → 第二段声音开始（"正在切换…"→"主人好，我是xx"） | 越小越好（理想 < 1s，受引擎加载限制） |
| **T3** | 日常播报（如首次天气播报）点击/触发 → 首句出声 | < 1s |

> 测量基准说明：`audio_start` 打点时刻 = 首段音频开始写入 AudioTrack（出声点）；`audio_end` = 整段播完。均为设备端时间戳，同一台设备上差值为精确耗时。

## 1.1 慢的构成（归因框架，测试时先分清是哪一段）

一次"点击切换 → 听到声音"的完整耗时由三部分叠加，**测试时必须区分**：

| 构成 | 含义 | 弱 CPU（车机）量级 | 能否优化 |
|---|---|---|---|
| **引擎加载** | 14MB onnx 模型读入内存 + FST 规则初始化（仅首次/切换新音色） | 10s~20s | 换更小模型可减半；缓存避免重复加载 |
| **合成推理** | VITS 逐帧生成音频（每字耗时） | 0.2s~1s/字 | 换更快模型/降语速系数；代码已到极限 |
| **播放** | AudioTrack 缓冲、写入 | 可忽略 | 无 |

- 若**首句出声慢**（T1 大）：多半是引擎加载或队列排队 → 看 `switch_click` 与 `audio_start` 间隔。
- 若**首句出声快但整段播完久**（T3 小、`audio_end` 距 `audio_start` 大）：是合成推理慢，属模型物理极限。
- 若切换时**第一段"正在切换"本身都要等**：点切换时引擎尚未就绪（warmUp 还在加载）或前序任务占线。

## 2. 测试前置准备

### 2.1 设备与连接
- 车机通过 adb 连接（无线 adb：`adb connect <车机IP>:5555`），或本机模拟器 `adb -s 127.0.0.1:5555`。
- 安装**包含测试打点日志**的 APK（`NuiTts` tag 下有 `switch_click` / `audio_start` / `audio_end` 日志的版本）。

### 2.2 ⚠️ 高德抢前台（必读）
NUI 首次启动后，会自动启动高德地图（默认启动延迟 5s），然后自动返回桌面（默认 10s 后）。**高德在前台期间，桌面设置面板会被盖住，点击无效**。

处理办法（任选）：
1. **等它返回**：启动 NUI 后先等 15 秒以上，确认回到 NUI 桌面再操作（推荐，模拟真实用户场景）。
2. **先杀掉**：`adb shell am force-stop com.autonavi.amapauto`——注意这只在当前 NUI 进程内有效；如果 NUI 进程被重启（force-stop NUI 后重新启动），会自动拉起高德，需再等一轮。
3. 临时把"地图"设置里的自动启动延迟调大（如 60s），测完再改回。

确认在前台：
```bash
adb shell "dumpsys activity top | grep ACTIVITY" | head -1
# 期望输出包含 com.nui.launcher（或 com.nui.launcher.debug）
```

### 2.3 干净状态（可选但推荐）
```bash
adb shell pm clear com.nui.launcher        # 正式包
# 或
adb shell pm clear com.nui.launcher.debug  # debug 包
```
> pm clear 会清掉天气缓存/语音状态，保证首次启动播报可复现（测 T3 时需要）。**注意：不测天气播报时不需要 pm clear**（避免天气链路干扰，见 3.4）。

## 3. 方法一：logcat 时间戳法（精确，推荐）

### 3.1 测 T1 / T2（切换男女声）

**步骤：**

```bash
# 0) 启动 NUI 并等待高德自动启动→返回（约 15s）
adb shell am start -n com.nui.launcher.debug/com.nui.launcher.MainActivity
sleep 15

# 1) 清空 logcat，保证时间线干净
adb shell logcat -c

# 2) 进入桌面设置 → 声音 tab（坐标以模拟器 1920x1080 为例，车机需按实际屏幕调整）
#    打开设置：应用列表页 → "桌面设置" → 声音
adb shell input tap 96 1016        # 进入应用列表
adb shell input tap 380 220        # 点"桌面设置"
adb shell input tap 488 580        # 点"声音"tab

# 3) 点击切换音色（男声/女声，坐标示例：女声(1084,260) 男声(1324,374)）
adb shell input tap 1324 374       # 切到男声

# 4) 等待播报完成（首次切换含模型加载，等 30s；已缓存场景 5s 足够）
sleep 30

# 5) 抓取时间线
adb shell logcat -d -s NuiTts
```

**输出示例（含两次切换）：**

```
09:16:52.619  switch_click gender=male        ← 点击时刻
09:16:52.869  audio_start                       ← "正在切换语音"出声
09:16:54.125  audio_end                         ← "正在切换语音"播完
09:16:54.887  sherpa-onnx 引擎就绪：zh_CN-chaowen
09:16:54.889  audio_start                       ← "主人好，我是超文"出声
09:16:56.941  audio_end                         ← 播完
09:17:33.396  switch_click gender=female       ← 再点切回女声（缓存命中）
09:17:33.608  audio_start                       ← "主人好，我是小雅"出声（无"正在切换"）
09:17:35.414  audio_end
```

**指标计算：**
- T1（首次切换）= `audio_start(52.869)` − `switch_click(52.619)` = **250ms**
- T2 = `audio_start(54.889)` − `audio_end(54.125)` = **764ms**（含引擎加载）
- T1（缓存命中）= `audio_start(33.608)` − `switch_click(33.396)` = **212ms**
- T1（启动时已预载同音色，点击即播）：**19ms**（实测）

### 3.3 ⚠️ 长播报占线场景（重点回归项）

**现象**：一次长播报（如天气播报，约 17s）正在播放时点击切换，若没有打断机制，切换要等长播报播完才执行（实测等待 12.5s 后才听到"正在切换"）。

**已实现打断机制**：任何新播报/切换先打断正在合成的旧播报（`audio_start` 应紧随 `switch_click`）。测试该场景：
```bash
# 1) pm clear 后首次启动，等 35s 让天气长播报开始
adb shell pm clear com.nui.launcher.debug
adb shell logcat -c
adb shell am start -n com.nui.launcher.debug/com.nui.launcher.MainActivity
sleep 35

# 2) 天气播报播放中立即进设置点切换（此时应有 audio_start 日志正在刷）
adb shell input tap 96 1016 && sleep 1
adb shell input tap 380 220 && sleep 1
adb shell input tap 488 580 && sleep 1
adb shell input tap 1324 374    # 点男声

# 3) 立即抓时间线
adb shell logcat -d -s NuiTts | grep -E "switch_click|audio_start|audio_end"
```
**判定**：`switch_click` 与下一个 `audio_start` 间隔应 < 1s（被打断的旧播报不再有后续 audio_end）。

### 3.4 无天气播报场景（用户实证：切换慢与天气无关）

用户实测环境**没有天气播报**（天气链路未触发）时切换依然慢。此场景下慢的构成只能是**引擎加载**或**合成推理**，测试步骤：

```bash
# 1) 不 pm clear（保留普通状态），正常启动 NUI，等 15s 等高德返回
adb shell logcat -c
adb shell am start -n com.nui.launcher.debug/com.nui.launcher.MainActivity
sleep 15

# 2) 进设置点切换（男→女或女→男），本次为"切到未加载过的音色"
adb shell input tap 96 1016 && sleep 1
adb shell input tap 380 220 && sleep 1
adb shell input tap 488 580 && sleep 1
adb shell input tap 1084 260    # 点女声

# 3) 等待播报完成（首次加载新音色给足 40s）
sleep 40
adb shell logcat -d -s NuiTts | grep -E "switch_click|audio_start|audio_end|引擎就绪|音色已切换"
```

**时间线解读**：
- `switch_click` → 下一个 `audio_start` 间隔 = **首音延迟**（应为旧引擎播"正在切换"，< 1s）
- `audio_end`（"正在切换"播完）→ 下一个 `audio_start`（"主人好"）间隔 = **切换总等待**（含新引擎加载）
- 若 `switch_click` 后直接出现 `audio_start`（无"正在切换"）且间隔大：说明点切换时旧引擎未就绪，warmUp 加载尚未完成——**属于"首次加载慢"**
- 若"正在切换"和"主人好"各自 `audio_start`→`audio_end` 都耗时数秒：**合成推理慢**（弱 CPU 逐字生成）

**判定**：首音 < 1s 即打断/流式生效；切换总等待主要由新引擎加载构成（车机 10s+ 属正常物理时间，二次切换应 < 0.5s）。

### 3.2 测 T3（日常播报首音）

```bash
# 0) 干净状态 + 启动（pm clear 后首次启动会触发 30s 后的天气播报）
adb shell pm clear com.nui.launcher.debug
adb shell logcat -c
adb shell am start -n com.nui.launcher.debug/com.nui.launcher.MainActivity

# 1) 等 40s（30s 定时播报 + 余量）
sleep 40

# 2) 抓时间线
adb shell logcat -d -s NuiTts | grep -E "audio_start|audio_end|引擎就绪"
```

**输出示例：**
```
09:14:31.189  sherpa-onnx 引擎就绪：zh_CN-xiao_ya (22050 Hz)
09:14:56.198  audio_start     ← 首句出声（"主人上午好，现在是…"）
09:15:12.861  audio_end       ← 全段播完（16.9s 播完 80 字，边播边合成）
```
- T3 = 触发时刻（30s 定时器到期，即引擎就绪后 ~25s 处）→ audio_start。若需精确触发时刻，可在触发代码处加 `trigger_weather_voice` 打点；无打点时按"定时器 30s"推算。

## 4. 方法二：人工秒表法（无 adb 兜底）

车机不方便连 adb 时用手机秒表：
1. 打开桌面设置 → 声音 tab。
2. 秒表归零，点击男声/女声，**听到第一声立即按停** → 记录为 T1。
3. 听"正在切换…"结束，**听到下一句"主人好…"立即按停** → 记录为 T2。
4. 同样方法测日常天气播报首音（首次启动后等 30s 左右会播报）→ T3。
5. 连测 3 次取平均值，记录到下表。

> 人工法只能到秒级、有主观反应延迟（约 +0.2~0.5s），适合快速判断"是否可接受"；精确数据以 logcat 法为准。

## 5. 结果记录表

| 场景 | 次数 | T1 (点击→出声) | T2 (段间隔) | 备注 |
|---|---|---|---|---|
| 首次切男声（需加载） | 1 | | | |
| 切回女声（缓存命中） | 2 | | | |
| 切男声（缓存命中） | 3 | | | |
| 日常天气播报首音 | 1 | | | T3 |

**判定标准**（车机）：
- T1 ≤ 1s：可接受（缓存命中时应 ≤ 0.5s）
- T2 ≤ 2s：可接受（受引擎加载限制；加载过的音色应 < 0.5s）
- T3 ≤ 1s：可接受
- 若 T1/T3 显著超 1s：记录 logcat 供分析（确认是引擎加载慢还是合成慢）

## 6. 已知限制与说明

- **合成推理耗时**（整段播完时间）随文本长度线性增长（约 0.2s/字，弱 CPU 上更慢），这是模型物理极限；流式方案保证**首句 0.3s 内出声**，不保证整段播完时间。
- logcat 时间戳为设备本地时间，同一设备内差值准确；跨设备比较时需校准时钟（少见，一般不用）。
- 车机屏幕坐标与模拟器不同，`input tap` 坐标需用 `uiautomator dump` 或截图重新定位。
